# Vendomat V5 concept

**Date:** 2026-10-07. **Status:** Proposed. **Supersedes:** V4 and its phase programme, and the
first V5 draft in `CONCEPT.md`. **Keeps:** the observed native facts in `NATIVE-BASELINE.md`.

**2026-10-08 refinement:** [Named paths and drive identity](./REFINEMENT-2026-10-08.md) records
the new 4 TB boot drive plan. It supersedes the storage move and in-place server conversion below.

## Purpose

One owner runs three machines and about forty small repositories. Nix and devenv can already
compose all of it. Writing that composition by hand is the cost.

Vendomat removes the hand-writing. You declare what you want in a flat list and a table of
settings. Vendomat works out the rest of the graph, pins it, builds it once, and serves it to every
machine from one cache.

## The claim

Three statements, each testable:

1. You declare inputs one level deep. Vendomat resolves the whole transitive graph.
2. You configure a machine in TOML. No hand-written Nix for anything declarative.
3. Any build that happens once happens once. Every other machine substitutes it.

## Three layers

| Layer | Who writes it | Contents |
| --- | --- | --- |
| Yours | You | `vendomat.toml`, `<host>.toml`, `devenv.nix` |
| Generated | `vendomat sync` | `devenv.yaml` with exact revisions |
| Native | Nix, devenv, NixOS, Home Manager | Merging, conflict detection, substitution, activation |

You never edit the generated layer. You never write merge logic: the NixOS module system does that,
and a conflict is an evaluation error rather than a silent overwrite.

## Vocabulary

No new terms. An **input** is a repository that exports modules. An **import** uses one. A
**script** is a command devenv puts on `PATH`. All three are devenv's own words.

## Cores and deltas

Everything inherits from a minimal core and adds only what it needs. This holds at every layer.

| Layer | Core holds | A delta adds |
| --- | --- | --- |
| Machine | Boot, filesystems, network, users, nix settings, Tailscale | The host TOML |
| Shell | zsh, atuin, starship | Role scripts and aliases |
| Editor | `neovim-unwrapped` and the settings every variant needs | Its own plugins and rc |
| Python | The pinned interpreter and the uv2nix base | Project dependencies |

A core holds only what **every** consumer needs. It holds no opinion a consumer might not want. An
editor core carries no colour scheme, no finder, and no language server configuration.

### A core exports a function, not a package

This is the whole mechanism, and it needs no Vendomat code. A package is final: you cannot subtract
a plugin from a wrapped editor. A function takes a consumer's additions and returns a build.

```nix
# nvim-core/lib/default.nix
pkgs: { appName, plugins ? [ ], lua ? "" }:
pkgs.wrapNeovimUnstable pkgs.neovim-unwrapped {
  wrapRc = true;
  luaRcContent = coreLua + lua;
  plugins = corePlugins ++ plugins;
}
```

A variant is then three lines:

```nix
# notes-sidebar
editor = nvim-core.lib pkgs {
  appName = "notes";
  plugins = [ loci-nvim.packages.${pkgs.system}.plugin ];
  lua = ''require("loci").setup { }'';
};
```

So the convention is: **a core input exports `lib`.** Variants call it. Nothing else changes.

### Why this is cheaper than inheriting from a full build

Nix shares store paths. Every variant derived from one core shares `neovim-unwrapped` and every
plugin they have in common. The only new store content per variant is its wrapper, its rc, and its
own plugins.

Five editor variants therefore cost one core closure and five small deltas. The cache serves the
core once.

Inheriting from a full build has the opposite shape: every variant drags the whole plugin set
whether it uses it or not.

### The inheritance graph is the input graph

A variant lists its core in its own `devenv.yaml`. The resolver already walks that and deduplicates,
so one core serves every variant that names it. Inheritance needs no separate mechanism.

### Isolation for a variant

Three layers, all native:

1. A distinct binary name, reached by absolute store path. Nothing shadows the daily editor.
2. `wrapRc = true`. The variant ignores the user's own configuration.
3. `NVIM_APPNAME`. Separate state: its own shada, swap, and undo files.

`nvim-review` has the first two. Add the third wherever a variant must not share state.

# Worked example: a full system configuration

## File layout

```text
nix-meta/
  flake.nix
  vendomat.toml              you edit
  machines/
    desktop.toml             you edit
    desktop.nix              the part TOML cannot express
    hardware/desktop.nix     generated by nixos-generate-config
  profiles/secrets.nix
```

## `vendomat.toml` — the flat list

One line per input. Versions, never revisions. Vendomat maps a version to a git tag to a revision.

```toml
[inputs]
nvim-review = "*"
knappy      = "^0.3"
gitman      = "*"
```

There is no `needs` table here. Each input declares its own needs in its own `devenv.yaml`, and
Vendomat reads them. You never restate another repository's dependencies.

## `machines/desktop.toml` — the declarative settings

Every key is a real NixOS or Home Manager option path. Nothing is invented.

```toml
[options]
"networking.hostName" = "desktop"
"time.timeZone"       = "America/New_York"

"services.tailscale.enable" = true
"services.openssh.enable"   = true

"nix.settings.max-jobs"      = 8
"nix.settings.trusted-users" = ["andrew"]
"nix.settings.extra-substituters" =
  ["https://server.tail770f47.ts.net/attic/vendomat"]
"nix.settings.extra-trusted-public-keys" =
  ["vendomat:SRJCMEnuScYDRmGId+o9nkXn+MaLpQvDTHs5AfnRQgA="]

"environment.systemPackages" = ["ripgrep", "fd", "jq", "htop"]

"programs.atuin.enable" = true
"programs.atuin.settings.sync_address" =
  "https://server.tail770f47.ts.net/atuin"
"programs.atuin.settings.filter_mode" = "host"

"programs.zsh.shellAliases.ll" = "ls -la"
"programs.zsh.shellAliases.g"  = "git"

# Your own software. Same option shape as any upstream module.
"programs.nvimReview.enable"    = true
"programs.nvimReview.maxLength" = 100
```

A bare string in a package list resolves to `pkgs.<name>`. Everything else passes through as
written.

## `machines/desktop.nix` — the remainder

TOML cannot express a function, `mkIf`, `mkForce`, string interpolation, or a reference to another
option. Those stay in Nix. So does hardware and so do secrets.

```nix
{ pkgs, vendomat, ... }:
{
  imports = [
    ./hardware/desktop.nix
    ../profiles/secrets.nix
    (vendomat.lib.fromToml ./desktop.toml)
    vendomat.nixosModules.fromManifest
  ];

  users.users.andrew = {
    isNormalUser = true;
    extraGroups = [ "wheel" "networkmanager" ];
    shell = pkgs.zsh;
  };

  system.stateVersion = "26.11";
}
```

`fromToml` converts the table above into real options. `fromManifest` reads the resolved input set
and installs what this host asked for.

## `lib/fromToml.nix` — the converter, in full

```nix
{ lib, pkgs }: file:
let
  toml = builtins.fromTOML (builtins.readFile file);
  resolve = v:
    if builtins.isList v && builtins.all builtins.isString v
    then map (n: pkgs.${n} or n) v else v;
in
lib.mkMerge (lib.mapAttrsToList
  (path: value: lib.setAttrByPath (lib.splitString "." path) (resolve value))
  toml.options)
```

Ten lines. `mkMerge` keeps the module system's conflict detection intact, so a setting defined both
in TOML and in Nix fails loudly.

## Applying it

```sh
vendomat set services.openssh.enable true   # writes the TOML
vendomat diff                               # shows the real option delta
vendomat apply                              # drives nixos-rebuild switch
vendomat rollback
```

`diff` evaluates `nixosConfigurations.<host>.config.<path>` before and after, then compares the
JSON. It reports what a change does before activation.

# Worked example: a consumer project

```text
myproject/
  vendomat.toml      you edit
  devenv.nix         you edit, standard devenv only
  devenv.yaml        generated
```

```toml
# vendomat.toml
[inputs]
knappy      = "^0.3"
nvim-review = "*"
```

```nix
# devenv.nix — standard devenv options, nothing invented
{
  languages.python.enable = true;

  nvimReview.enable = true;

  scripts.check.exec = "testee verify --mode quick";
  scripts.gs.exec    = "git status --short";
}
```

```yaml
# devenv.yaml — GENERATED by `vendomat sync`. Do not edit.
inputs:
  nixpkgs:
    url: github:cachix/devenv-nixpkgs/rolling
  knappy:
    url: "git+file:///home/andrew/vendor/knappy?rev=4f1c9ae…"
  nvim-review:
    url: "git+file:///home/andrew/vendor/nvim-review?rev=bd26fea…"
  fsdantic:
    url: "git+file:///home/andrew/vendor/fsdantic?rev=81a0c22…"
imports:
  - knappy
  - nvim-review
  - fsdantic
```

`fsdantic` appears because `knappy` needs it. You never named it. The generated file carries exact
revisions, so it is also the lock.

Use `scripts` rather than shell aliases. A script is a real executable in the store, so it works in
a subshell, a Makefile, an editor, and over SSH. devenv orders `scripts` first on `PATH`, so a
script can also shadow a package of the same name.

# Worked example: authoring one of your own inputs

Four lines produce all three native faces.

```nix
# knappy/flake.nix
let
  modules = vendomat.lib.mkModules {
    name = "knappy";
    packages = cfg: pkgs: [ self.packages.${pkgs.system}.default ];
  };
in {
  devenvModules.default      = modules.devenv;
  nixosModules.default       = modules.nixos;
  homeManagerModules.default = modules.homeManager;
}
```

Options land at `knappy.*` under devenv and `programs.knappy.*` under NixOS and Home Manager.

Anything that does not map across all three faces goes through `extra`, written in that target's
own language:

```nix
vendomat.lib.mkModules {
  name = "linkman";
  options.port = lib.mkOption { type = lib.types.port; default = 8080; };
  packages = cfg: pkgs: [ self.packages.${pkgs.system}.default ];

  extra = cfg: pkgs: {
    nixos.systemd.services.linkman = {
      wantedBy = [ "multi-user.target" ];
      serviceConfig.ExecStart =
        "${self.packages.${pkgs.system}.default}/bin/linkman --port ${toString cfg.port}";
    };
    devenv.processes.linkman.exec = "linkman --port ${toString cfg.port}";
  };
}
```

A system service, a user service, and a devenv process are three different mechanisms with three
different lifetimes. `extra` keeps them honest instead of inventing a fourth.

When the same shape appears in `extra` for a third input, promote it to a real `mkModules` key. By
then three concrete uses define its shape.

# The machinery

| Part | Role | Where |
| --- | --- | --- |
| Cache | One private Attic cache over Tailscale | `server`, 4TB NVMe |
| Source store | Git clones of every input | `~/vendor/<name>` |
| Resolver | Versions to revisions, transitive closure, generated `devenv.yaml` | `vendomat sync` |
| Builder | Builds each input on a new tag | `server`, systemd timer |
| Push | `attic watch-store` | every machine |

## Why builds are fast

The builder builds each input **separately** when its tag lands. Each closure reaches the cache on
its own. A project that assembles twelve inputs substitutes twelve ready closures and compiles
nothing. Nothing new implements this. It follows from one derivation per input and one cache.

Every target is `x86_64-linux` and the builder is `x86_64-linux`. One build serves every machine.
No matrix and no cross-compilation.

## Publication is ambient

There is no publish operation and no retain operation. The builder builds. `watch-store` pushes.
Other machines substitute on demand. The build log and its exit status are the durable record of
what was checked against which bytes, so Vendomat writes no receipt.

## Durable state

**Vendomat owns none.** The cache belongs to Attic. `~/vendor` is a cache of git remotes. `.vend/`
holds out-links from `nix build --out-link`, which are indirect garbage-collection roots, so
retention needs no Vendomat code. The build record belongs to CI. Every class is native-owned or
regenerable.

## Authority

Native declarations and locks select. devenv composes. Nix builds and substitutes. Attic stores and
signs. NixOS and Home Manager activate. Version control keeps history.

Vendomat resolves versions to revisions, writes generated files, keeps clones, and reports.

One change from V4: Vendomat now picks revisions. A resolution can be wrong. The generated
`devenv.yaml` keeps it honest, because it is git-tracked, diffable, and exact. Pin a revision
directly to escape a bad resolve.

# The library

**Python, about 400 new lines**

| File | Role | Lines |
| --- | --- | --- |
| `registry.py` | Read and write `vendomat.toml` | 60 |
| `resolve.py` | Version to tag to revision; read each input's `devenv.yaml`; walk; dedupe | 120 |
| `emit.py` | Write the generated `devenv.yaml` | 40 |
| `cache.py` | Presence checks with `nix path-info --store` | 50 |
| `store.py` | Clone and fetch into `~/vendor` | 30 new; `sources.py` has the rest |
| `systemcfg.py` | `set`, `get`, `unset`, `diff`, `apply`, `rollback` over the host TOML | 120 |
| `cli.py` | Command surface | 100 new |

**Nix, about 105 lines**

- `mkModules.nix` — one declaration to three adapters (30)
- `fromToml.nix` — TOML to NixOS options (10)
- `module.nix` — consumer module: substituter, key, credential path, `.vend/` out-links, `explore` (40)
- `fromManifest.nix` — install what this host resolved (25)

**NixOS, about 70 lines in `nix-meta`**

Substituter, trusted key, `trusted-users`; `attic watch-store`; the build timer and its script; the
`atticd` storage move.

## Observed mechanisms

Each was run on the pinned tools. The design depends on them.

| Fact | Observed |
| --- | --- |
| `git+file://…?rev=` locks a real revision and NAR hash | 2026-10-07, Nix 2.34.7 |
| Dotted-path TOML converts to nested NixOS options, with package names resolved | 2026-10-07 |
| devenv has no `aliases` option; `scripts` sort first on `PATH` by `meta.priority` | devenv `fe20b5c`, `src/modules/top-level.nix:353` |
| `attic push` drops upstream-sourced paths unless the filter is cleared | 2026-10-07, P5 |
| Neovim wrappers default to `--suffix PATH`, so a command needs its absolute store path | P1 |
| devenv merges an imported `devenv.yaml` only for local paths inside the git root | P2 |

The last fact is why `devenv.yaml` is generated: a transitive graph has to arrive flattened in the
consumer's own file.

## Boundaries

Vendomat is not a daemon, a deployment engine, a retention engine, a cache protocol, an audit
system, or a second lock. It writes no receipt. It makes no machine-generation claim. It does not
replace the NixOS module system; it feeds it.

# Build order

The 2026-10-08 refinement changes the server bootstrap: build a new boot and root filesystem on
the 4 TB drive, and keep the 512 GB installation intact. Rewrite the guide's install steps before
running them. The sequence below is the earlier draft for the remaining library work.

**Starting state: a bare repository. All work happens on `server`.** The laptop (`framework`) is a
switchover at the end, not a proving ground.

`nix-meta/flake.nix:289` records that the earlier `wsl` and `desktop` hosts were retired. `server`
is the only live host and it runs `atticd` and the builder.

## Server builds. Framework collects.

Every step runs on `server`, in place, with `nixos-rebuild test`. By the time the laptop is
installed, `server` has already built and pushed every closure it needs. The laptop's install is
therefore a download, not a build.

That makes the laptop switchover both cheap and the cold-consumer proof — the one V4 P5 could not
obtain — collected as a by-product rather than chased as a gate.

A virtual machine stays the pre-flight check: `nixos-rebuild build-vm` boots the core with an empty
store before `server` is touched.

## Core and delta

| | Core | Delta |
| --- | --- | --- |
| Shared | Boot, filesystems, network, users, nix settings, Tailscale, SSH | — |
| `server` | — | `atticd`, the builder, restic, headless services |
| `framework` | — | Graphical session, Hyprland, power management, wifi, suspend |

Anything only one machine needs is a delta. The core is what both need to boot and be reachable.

| Step | Work | Needs Python | Result |
| --- | --- | --- | --- |
| 1 | The machine core | No | One module both machines share |
| 2 | Cache access inside the core | No | A new machine substitutes from first boot |
| 3 | `nixos-rebuild build-vm` on the core | No | The core boots with an empty store |
| 4 | `mkModules` and `fromToml` in `lib/` | No | Four-line inputs; TOML host settings |
| 5 | Split `nvim-core` out of `nix-nvim` | No | The core-and-delta shape proved |
| 6 | `attic watch-store` and the builder on `server` | No | Every build reaches the cache |
| 7 | Convert `server` with `nixos-rebuild test`, then `switch` | No | One machine on the new pattern |
| 8 | `registry`, `resolve`, `emit` | Yes | `vendomat sync` writes `devenv.yaml` |
| 9 | `systemcfg`: `set`, `get`, `diff`, `apply`, `rollback` | Yes | `server` configured from TOML |
| 10 | Install `framework` | No | A warm cache serves it; `CACHE-007` falls out |

Steps 1 to 7 need no Python. The whole Nix layer stands up before the resolver exists, so a broken
resolver can never stop a machine booting.

## Activation

`nixos-rebuild test` activates without changing the boot default, so a reboot recovers the previous
generation. Promote to `switch` after the configuration has run for a while. Do not
garbage-collect a generation until its replacement has survived a reboot.

## Done looks like

From a project that has never used Vendomat: add one line to `vendomat.toml`, run `vendomat sync`,
enter the shell, and use the library with no local build.

Then: `vendomat set programs.nvimReview.enable true`, `vendomat diff`, `vendomat apply`, and the
command is on the machine.

Two tests, one afternoon, one machine.

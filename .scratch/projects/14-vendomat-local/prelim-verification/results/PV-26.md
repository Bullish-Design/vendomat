## Why this was safe for the running machine

`nix-meta` pins `vendomat` to an exact revision (`d5a90f0`), and the command installed on `server` is a store path. A purge on `main` changes neither. The old code stays alive on the machine until `nix-meta` repins. This is a named, temporary state with its own backlog.

## About the plane

The V4 plane (`plane.py`, about 1,100 lines) kept the Dagu workflow registry as numbered, immutable generations: render each project's workflows with `devman`, validate them, switch the `active` pointer, and roll back. The live Dagu service on `server` reads `~/.local/state/vendomat/devman/active`, which points at generation 4. The V5 concept already gives each part: a NixOS generation is the atomic switch and the rollback (`vendomat apply` and `rollback` drive `nixos-rebuild`), `devman`'s flake already builds the renderer and Dagu and validates workflows in a Nix check, and the project list is a list of inputs. What is missing is on the `devman` side (a function that renders the registry from project inputs) and in `nix-meta` (`registryDir` set to that store path). I read the plane docstring, `devman/USER.md` section 2.7, the `nix-meta` profile, and the `devman` flake outputs. I did not read the renderer or run a plane command.

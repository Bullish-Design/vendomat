# PV-25 — is the system `vendomat` reachable from a devenv project shell? (`DEL-010`)

**Date and time:** 2026-10-09, 09:15 to 09:30 (local)
**Host:** `server` (x86_64-linux). System generation 149, `vendomat` 0.5.0 at `/run/current-system/sw/bin/vendomat`.
**State:** passed for two project shapes. One related defect found (item 3 below). Not run in an existing repository.
**Related requirements:** DEL-010, DEL-011, DEL-007.
**Tools:** devenv from the session (the same one `devenv shell` uses in the repositories); Nix 2.34.7; Git 2.54.0.
**Fixtures:** `~/.local/state/vendomat/v5/2026-10-08/fixtures/del010/` — `bare` (a `devenv.yaml` with `nixpkgs` and an empty `devenv.nix`), `consumer` (the same, plus `devenv.nix` importing `/run/current-system/sw/share/repoman/module/devenv.nix` and `/run/current-system/sw/share/vendomat/consumer-module.nix`, as the central overlay does for `argentic`, and a V5 `vendomat.toml`), and `probe.sh`. Both are throwaway Git repositories outside every real repository. No real repository's `devenv.lock` was touched. Raw output is in `~/.local/state/vendomat/v5/2026-10-08/logs/del010/`.
**Probe:** `devenv shell -- probe.sh` prints the first `vendomat` on `PATH`, its target, every match, whether `path` and the `sync` flags exist, and whether a `vendor-sync` script exists.

## A first run was wrong

My first run (`bare`, logged as `A-bare.txt`) found the venv `vendomat` of this repository first. The cause was my own session: it started inside this repository's devenv shell, so the child inherited that `PATH`. That result says nothing about a project shell. I reran with the parent environment scrubbed: every `PATH` entry under `/Documents/Projects/vendomat/` removed, and the `DEVENV_*`, `VIRTUAL_ENV`, `IN_NIX_SHELL`, and `DIRENV_*` variables unset.

## Observations (scrubbed parent environment)

1. **`bare`:** the first and only `vendomat` is `/run/current-system/sw/bin/vendomat`, which resolves to `vendomat-0.5.0`. `path` exists. `--collection` and `--dry-run` exist.
2. **`consumer` (imports the repoman and the vendomat consumer modules):** the same result. One match, the system 0.5.0, with `path` and both flags. Under machine delivery the module adds no `vendomat` package of its own, as its source says. The `vendor-sync` script is not on `PATH`.
3. **Defect in the `consumer` shell.** Entering the shell printed `vendomat install-hook: vendomat.toml must contain at least one [[replacement]] table`. The V4 module runs `vendomat install-hook` on shell entry, and the command still exists. It reads the project's `vendomat.toml` in the V4 format, and the V5 registry (`[forge]`, `[inputs]`) does not fit. The shell still started (exit 0). No `pre-push` hook was installed.
4. **`devenv shell --clean` (`bare`):** no `vendomat` is found. That mode drops the system `PATH`. This is the behavior of `--clean`, not of the install.

## Inference

For a normal project shell, a host-installed command is reachable and nothing else shadows it, as long as the shell does not start from another project's environment and does not use `--clean`. The V4 module does not add a second copy under machine delivery. This is what `DEL-010` asks for, on two fixture shapes. `DEL-011` is not met yet: the CLI is still delivered with the V4 module installed beside it, and that module is the one that breaks on a V5 `vendomat.toml`.

## Not covered

- I did not enter an existing repository's shell (`argentic`, `loci-core`, and so on): that can rewrite its `devenv.lock`. The `consumer` fixture mirrors their imports.
- `framework` and any host other than `server`.
- The effect of `direnv` and `.envrc` on `PATH` in a real repository.
- Which real repositories have a `vendomat.toml` in the V4 format. Those still need the V4 module.

## Follow-up

Replace or guard the V4 consumer module before any real repository adopts a V5 `vendomat.toml` (`DEL-011`). The smallest guard: skip `install-hook` when `vendomat.toml` has no `[[replacement]]` and has `[inputs]`. That is a code change to V4 provenance, so it needs a decision first.

# Part 1. The four Machines limits

## 1. Pin one devenv for the whole system

**What we face (agent G, proven):**

- The command line never compares revisions. It compares its own version string with the modules'
  `src/modules/latest-version` file (`update-check.nix:73-107`, `config.rs:929`).
- An unpinned project locks the devenv modules to `main` at lock time, not to the command line's
  revision.
- The `v2.4.0` tag is stale for this purpose: at `b904dcb5`, `latest-version` says `2.3.1`. The first
  revision that says `2.4.0` is `a5c34429421e077df6f8f133e502617bedc22206` (2026-09-26). It differs
  from the tag only by three non-Machines fixes.
- `require_version` accepts `true`, `"2.4.0"`, `"=2.4.0"`, `">=2.4.0"`, `">=2.4.0, <2.5.0"`, `"2.*"`.
  It rejects `~` and `^`. A string constraint is enforced by every build of the command line.
  `true` is enforced only by a release build: `pkgs.devenv` from nixpkgs is one; the upstream flake
  build (installed here today) is not.
- Today: 58 project locks, 56 readable, **26 different devenv revisions** (modules 1.6.1 to 2.4.0).
  No project sets `require_version`. `nixvim/devenv.lock` and `nix-nvim/devenv.lock` hold jj
  conflict markers and are not valid JSON.
- **devenv 2.4.0 bug:** `devenv machines install` hangs at the first `nix copy` when the machine has
  any install payload (`install.secrets`, `install.extraFiles`, `install.encryptionKeys`). Upstream
  issue #3254, fixed on `main` by `a5fd551a` (#3255, 2026-10-08), not released. The fix was proven
  with a `main` build (`2.4.1+a73c5b8`).

**Mechanism:**

1. The core NixOS module installs one devenv command line from one pin. Use `pkgs.devenv` from the
   system's pinned nixpkgs, so `require_version: true` also works.
2. Every project and the systems repository set `require_version: "2.4.0"` and
   `inputs.devenv.url: github:cachix/devenv/a5c34429421e077df6f8f133e502617bedc22206?dir=src/modules`.
3. A check fails when a lock pins another revision or `require_version` is missing. Agent G's
   `devenv-pin-check.py` does this read-only (in `raw/agent-g-machines-pinning.md`). Run it in each
   repository's Testee gate and in a fleet-wide scan.
4. For the first install, either use no install payloads on 2.4.0, or run that one install with a
   `main` build (`nix run github:cachix/devenv/<rev>#devenv -- machines install …`). Move the pin to
   2.4.1 when it is tagged.

## 2. Root SSH

It is configuration. Proven in a VM (agents F, G):

- `target.host = "root@localhost"` works. The machine deploys to itself.
- Run devenv as `andrew`. As root it fails with `cannot remount "/nix/store" writable: not in a
  private mount namespace`, unless `NIX_REMOTE=daemon` is set.
- Required in the new config: `users.users.root.openssh.authorizedKeys.keys = [ <andrew's deploy key> ]`,
  `PermitRootLogin prohibit-password` (already set on `server`), and a `known_hosts` entry.
  `install` refuses a config that gives root no SSH key or password (`machines.rs:1664`).
- When the target's receiving user is root, `nix copy` needs no signatures. A non-root receiving user
  failed with "lacks a signature by a trusted key".

*Inference, not tested:* restrict the root key with an `authorized_keys` `from="127.0.0.1,::1,<tailnet range>"`
option. `andrew` already has `sudo`, so the key adds no new privilege, only a new path to it.

## 3. Wrap the wipe with a check

**What can go wrong (all proven in VMs):**

| Hazard | Evidence |
| --- | --- |
| devenv's default disko mode runs disko's legacy `diskoScript`: destroy, format, mount, **no prompt** | disko `lib/default.nix:1034-1045`; devenv `machines.rs:1991-1993` |
| Destroy modes run `umount -Rv /mnt` first; a tmpfs on `/mnt` was unmounted | disko `lib/default.nix:909,954`; agent F `q2-mnt-disko.log` |
| `--disko-mode format` does not mount; the next install step **wrote a 2.6 GB system into the running root** | agent F `q2-format-mode*.log` |
| Two disks with the same disko partition labels: after a reboot, `by-partlabel/disk-main-root` pointed at the **old** disk | agent E `q2a-raw.txt` |
| `canTouchEfiVariables = true` puts the new disk first in `BootOrder` | agents E, F |
| Disko wipes only disks it lists: an unlisted disk kept an identical raw SHA-256 through every mode | agent E `q3-final.txt` |

**Two layers, so that a bypass still fails:**

1. **Evaluation assertions in the machine config (always enforced).** devenv builds the system
   before disko touches a disk (`machines.rs:1681`, "Realise the complete replacement before any
   disk mutation"). So a NixOS `assertions` entry stops `devenv machines install` even when someone
   skips the wrapper. Assert that:
   - every `disko.devices.disk.*.device` is a `/dev/disk/by-id/` path that the host inventory names
     as an install target, and never the `previous-system` or any other inventory disk;
   - the disko disk attribute name is unique to the host (no partition-label collision);
   - every `fileSystems.*.device` is `by-uuid` or `by-partuuid`, never `by-partlabel` or a kernel name;
   - `boot.loader.efi.canTouchEfiVariables` is false while the host's `firstInstall` flag is set.
2. **A runtime preflight (Vendomat command, run over the same root SSH before `disko`).** It checks
   what evaluation cannot see: the target by-id resolves, its model, serial, and size match the
   inventory, `wipefs --no-act` and `blkid -p` show no signature, it does not back the running root
   or `/boot`, `/mnt` has no mounts, and a committed `facter.json` exists. Then it runs
   `devenv machines install <host> --phases disko,install` with the default disko mode. It refuses
   `--disko-mode format` and `mount`.

The wrapper is the "type yes" step that disko's legacy script lacks. Proposed: `vendomat machine install <host>`.

## 4. Installing onto the 4 TB drive, keeping the 512 GB drive

Agent F ran every route in a QEMU VM with two NVMe disks and persistent OVMF NVRAM.

| Route | What runs | Downtime | Risk to the 512 GB drive | Proven |
| --- | --- | --- | --- | --- |
| a. Partition by hand, then `nixos-install --system <prebuilt>` | On the live `server` | none until cutover | `/mnt` use. A disko-built system expects disko partition labels; plain `sfdisk` partitions **did not boot** ("Timed out waiting for device /dev/disk/by-partlabel/disk-main-root") | install yes, boot no |
| b. `disko-install` v1.13.0 | On the live `server` | none | none with default flags | **failed as shipped**: `xcp` hit "Read-only file system (os error 30)" copying the store; worked only after patching `xcp` to `cp -a`. It also needs a flake `nixosConfigurations`, not Machines |
| **c. `devenv machines install --phases disko,install`, `target.host = "root@localhost"`, run as `andrew`** | On the live `server` | none until cutover | `umount -R /mnt`; NVRAM only if `canTouchEfiVariables = true` | **yes**: 68 s in the VM; disk A's partition table, ESP files, and NVRAM entries unchanged; disk B booted alone |
| d. Boot an installer USB, run `--phases facter,disko,install` | Controller on the USB or another host | the whole install | low: disk A not mounted | yes, with a custom ISO (the stock ISO lacks `nixos-facter` and `nix-command`) |
| e. Full install with kexec from another host | Another host | ~71 s in the VM, longer on hardware; services stop with **no clean shutdown** (`kexec -e`) | disk untouched in the VM | yes; needs internet for the kexec image |
| f. Move the drive to another machine | Another machine | none for `server` | none | partly; the facter report must come from `server` |

**Firmware fallback (proven in the VM, not on `server`'s firmware):**

- With `canTouchEfiVariables = false`, the builder passes `bootctl --variables=no`. NVRAM stays as it
  is. The new ESP still gets `\EFI\BOOT\BOOTX64.EFI`, so the firmware can boot it.
- To try the new disk once: `efibootmgr -C -d /dev/disk/by-id/<4TB> -p 1 -L newsys-trial -l '\EFI\systemd\systemd-bootx64.efi'`
  creates an entry outside `BootOrder`, and `efibootmgr -n <entry>` boots it once. The next boot
  returns to the 512 GB system.
- systemd-boot has no `efiInstallAsRemovable` option. Only GRUB, Limine, and rEFInd have it.

**Recommendation: route c**, wrapped by the check in item 3:

1. Write the new systems repository (D2). Give `server` a disko layout on the 4 TB by-id, with a
   unique disk name, preset partition GUIDs and filesystem UUIDs, mounts by UUID, and
   `canTouchEfiVariables = false`.
2. Prove the layout in a disko VM test (`lib.testLib.makeDiskoTest`; `diskoImages` fails on the
   current nixos-unstable).
3. As root on `server`, run `nix run nixpkgs#nixos-facter > facter.json` once. Commit it as
   `.machines/server/facter.json`. `nixos-facter` is not on root's `PATH` today.
4. Add the deploy key for root on the **current** system, by hand, for this one install.
5. Run `vendomat machine install server` (the preflight, then `--phases disko,install`).
6. Unmount `/mnt`. Create the one-time boot entry and reboot with `efibootmgr -n`.
7. If the new system fails, power-cycle: the firmware returns to the 512 GB system.
8. After the new system has run reliably, set `canTouchEfiVariables = true`, run `bootctl install`
   once, and remove the stale Windows entry.

Route d is the fallback plan if you want nothing running from the old system during the install.

# Part 2. Decisions

## D1. Why a workspace is not "just a devenv shell", and what Vendomat adds

A workspace **should** be a devenv shell. The earlier gap was that V5 sends a project shell through
devenv's flake mode. A plain `devenv.nix` + `devenv.yaml` + `devenv.lock` workspace has the full
command line. Agent H then proved what such a workspace still lacks for your goals:

| # | devenv behaviour (2.4.0) | Proven by | What Vendomat must add |
| --- | --- | --- | --- |
| 1 | A flake input's own flake inputs **are** locked transitively, and `imports = [ inputs.x.devenvModules.default ]` works | H Q1, Q2 | Nothing. This is the path to use |
| 2 | A module imported as a directory (`imports: [lib-b/devenv]`) ignores that repo's `devenv.yaml`: "attribute 'lib-c' missing" | H Q3 | Export devenv faces as flake attributes, or flatten the inputs |
| 3 | A `follows` deeper than one level (`lib-a.inputs.lib-b.inputs.nixpkgs.follows`) is dropped silently | H Q1; `lib.rs:116-154` | Flatten or lint `follows` |
| 4 | With a cold Nix fetcher cache and the collection down, `devenv shell` fails, with or without `--offline`, though the store holds the source. `devenv update` fails but exits 0 | H Q4; PR #3244 open | A prefetch or store check; read the lock, not the exit code |
| 5 | No command prints a locked input's store path | H Q5 | `vendomat path` reading `devenv.lock` (a working one-liner exists, offline) |
| 6 | No tag-pin policy; branch refs are accepted, also transitively | H Q6 | `check_pins.py` (works, walks the lock) |
| 7 | Cache push is Cachix-only; no post-build hook or `devenv:build` task | H Q7 | `devenv build` → `attic push --stdin`, or `attic watch-store` |
| 8 | Profiles from `inputs.X.devenv.config` references do not apply; profiles from imported modules do | H Q8 | Use imports, not references |
| 9 | Projects drift across 26 devenv revisions | G Q1 | The pin check (Part 1, item 1) |

**Options for the Vendomat layer:**

- **A. Commands only.** Workspaces stay hand-written devenv. Vendomat adds `check` (pins, version,
  nested follows), `path`, `push`, `prefetch`.
  - Pros: least code; devenv files stay native and hand-editable; no Vendomat input.
  - Cons: the owner still writes every input, `follows`, and import by hand; the rules are checked,
    not produced.
- **B. A Vendomat devenv module in every workspace.** It adds tasks (a pin check before
  `devenv:enterShell`), `outputs.inputPaths`, and the Attic push.
  - Pros: automation runs inside the shell.
  - Cons: every workspace takes Vendomat as an input, which `DEL-008` forbids today; a Vendomat
    change touches every shell.
- **C. Generated input fragment.** `vendomat sync` reads `vendomat.toml` and writes a directory, for
  example `.vendomat/`, with a `devenv.yaml` (direct inputs, tag pins, flattened `follows`) and a
  `devenv.nix` (the selected module faces, `outputs.inputPaths`, the push task). The project's own
  `devenv.yaml` has `imports: [ ./.vendomat ]`. devenv merges a local import's `devenv.yaml`, and the
  project's own file wins on conflicts (`config.rs:681-745`, agent D).
  - Pros: one registry drives source imports, module selection, and cache export; the project's
    files stay hand-editable; Vendomat is not an input (generated files only); the same generator
    serves workspaces and the systems repository (D2).
  - Cons: a new generator target. **The composition is unproven**: no fixture has yet imported a
    generated directory that declares inputs.
- **D. C plus A.** C produces the files; A's commands check and push.

**Recommendation: D.** First prove option C's composition in one fixture.

## D2. Full Machines adoption from a blank slate

Proven in VMs (agent G): a two-host layout (`server`, `framework`) with a shared core module,
per-host deltas, and Home Manager roles builds with nixos-unstable. Against a VM, the following all
work: `check`, `plan`, `deploy --yes`, `status`, redeploy, `rollback`, the watchdog (a failed health
check rolled back after `rollbackTimeout`), a Home Manager-only deploy, and a self-deploy. The
fixture `devenv.yaml` and `devenv.nix` are in `raw/agent-g-machines-pinning.md`. They are the start
of the real layout.

**What full adoption requires:**

1. A new systems repository from scratch (`devenv.yaml`, `devenv.nix`, `nixos/`, `home/`). `nix-meta`
   becomes reference only. Lock: `devenv.lock`.
2. Inputs: `nixpkgs` (nixos-unstable), the pinned `devenv` modules, `disko`, `home-manager`. Add
   `nixos-facter-modules` only if `hardware.facter` is not `null`. Machines always use
   `inputs.nixpkgs`. A different nixpkgs for shell packages needs a second input such as
   `nixpkgs-shell`.
3. A committed facter report per host, or `hardware.facter = null`. Without a report, the build fails
   ("path …/.machines/framework/facter.json does not exist").
4. Root SSH as in Part 1, item 2. Deploy as `andrew`.
5. Attic: `nix.settings` in the core module. devenv adds no substituter on the target. `nix.conf`
   matched a plain NixOS build exactly.

**Pitfalls to design for (proven):**

- Any failed systemd unit makes `switch-to-configuration` exit 4. The deploy then fails and rolls back.
  If a unit was already failing before the deploy, the rollback also failed (`phase: rollback-failed`).
  Every service needs a clean start, including its secrets.
- Home Manager is not rolled back.
- `plan` needs `/nix/var/nix/profiles/system` on the target. An installed NixOS has it.
- Interface churn: of 24 commits from `v2.4.0` to `main`, one touched Machines (the install fix).
  The whole Machines command line landed in one commit on release day. Diff `machines.nix` and
  `machines.rs` on every pin bump.

**Requirement impact.** `BOOT-008` ("A converted machine MUST reach every capability it had before")
and `BOOT-010` (match the replaced tree) conflict with "no reuse". `CLI-011` and `CLI-013` become
Machines commands (draft `CLI-017`, `CLI-018`, `CLI-019` in REPORT section 3.2). `BOOT-022`
("installed as a prebuilt closure" with `nixos-install`) becomes route c. These need successor IDs.

## D3. Option C: what "Vendomat manages the modules" means

1. **Source imports.** `vendomat.toml` stays the single list of direct inputs, pinned to tags in the
   collection. Two outputs: today's generated `flake.nix` for library repositories that other flakes
   consume, and the D1-C fragment for devenv consumers (workspaces and the systems repository).
2. **Module selection.** The registry names which faces each consumer imports, for example
   `[modules] devenv = ["knappy"]` and `[machines.server] nixos = ["attic-server"]`. The generated
   `devenv.nix` writes `imports = [ inputs.knappy.devenvModules.default ]` (proven to work, agent H Q2).
   For machines it writes the module list into `machines.<host>.nixos`. Faces stay inert until
   `enable = true` (`INP-006`), so an import changes nothing by itself. This reverses `GEN-017`
   ("the generator MUST NOT … import any module face"), and needs a successor ID.
3. **Build-cache exports.** `vendomat push` builds the selected outputs or machines
   (`devenv build outputs.<x>` / `machines.<host>`) and pipes the store paths to
   `attic push <cache> --stdin`. The builder on `server` builds each library on a new tag. Unproven:
   a real Attic upload of devenv outputs (no Attic server in the fixtures).
4. **Not an input.** The generated files carry everything, so a consumer still declares no Vendomat
   input (`DEL-008` holds). Only `mkModules`, if built, would be an input of library authors (D4).

## D4. `mkModules`

`mkModules` is a proposed helper. A library calls it once with `{ name, options, packages, extra }`
and gets three modules back:

- `devenv`: options at `<name>.*`; installs the packages into the shell.
- `nixos`: options at `programs.<name>.*`; installs into `environment.systemPackages`.
- `homeManager`: options at `programs.<name>.*`; installs into `home.packages`.

Each module declares `enable`, default false. `extra` adds content for one module only, for example a
systemd service for NixOS and a devenv process for the shell. It exists so one library can serve a
workspace, a machine, and a user without three hand-written modules.

Why "convention now, helper later": PV-07 found 14 of 18 module providers with one face and one with
three. A helper now makes every library author take Vendomat as an input for little gain. With full
Machines adoption, more tools serve both a workspace and a machine, so the helper becomes more useful.

Options:

1. Build it now.
2. Write the convention and a check now: attribute names `devenvModules.default`,
   `nixosModules.default`, `homeManagerModules.default`; `enable` defaults false; each face evaluates
   alone and installs nothing until enabled. Build the helper when three libraries repeat the shape.
3. Drop it.

Recommendation: 2. One decision is needed either way: the option path per face. `knappy.*` under
devenv and `programs.knappy.*` under NixOS and Home Manager differ.

## D5. disko: the facts

All proven in NixOS VM tests (agent E) unless marked.

1. **Mounts.** With `device = "/dev/disk/by-id/…"`, disko writes mounts as
   `/dev/disk/by-partlabel/disk-<diskname>-<partname>` (`gpt.nix:81-90,146`). A partition `uuid` makes
   them `by-partuuid`. `lib.mkForce` to `by-uuid` works and boots.
2. **Preset UUIDs.** Partition GUIDs (`uuid`), ext4 (`extraArgs = ["-U" uuid]`), and vfat
   (`extraArgs = ["-i" "A1B2C3D4"]`) can be fixed before formatting. The system booted with them.
   So `DISK-005` ("record the actual UUIDs after formatting") can become "declare the UUIDs before
   formatting".
3. **Label collision.** Labels come from the disk attribute name. Two disks with the same labels
   collide, and after a reboot the label pointed at the old disk. Use a unique disk name.
4. **Scope.** Destroy touches only disks in the config. An unlisted disk kept an identical raw
   SHA-256 through every mode.
5. **Prompts.** The `destroy` and `destroy,format,mount` modes ask for `yes`. The legacy
   `diskoScript`, which devenv uses by default, does not.
6. **`/mnt`.** Destroy modes run `umount -Rv /mnt`.
7. **`disko-install`** installs from a running system with no reboot and no NVRAM write by default.
   In the VM test with agent E's flake it worked; with agent F's larger closure it failed as shipped
   (`xcp` "Read-only file system"). Root cause unproven. Not the recommended route.
8. **EFI.** `canTouchEfiVariables = true` adds the new disk first in `BootOrder`. `false` writes no
   NVRAM entry. Neither touches the other disk's ESP.
9. **Inert module.** devenv's injected `disko.nixosModules.disko` changes nothing when no disk is
   declared (identical toplevel derivation).
10. **Testing.** `lib.testLib.makeDiskoTest` works on nixos-unstable `e7439b6`. `diskoImages` and
    `vmWithDisko` fail there ("vmTools: the `kernel` argument … has no `target` attribute"). They work
    on disko's own locked nixpkgs.

**What remains unproven**, and why:

| Item | Why | How to close it |
| --- | --- | --- |
| A new NVRAM entry survives a reboot; `BootNext` and the firmware menu on `server` | OVMF in the test dropped guest-written entries, also in a plain `efibootmgr -c` control | On `server`: create the `-C` entry, run `efibootmgr -v`, reboot with `-n`; the 512 GB system stays the default |
| `nixos-facter` as root on `server` | Needs root | The owner runs `nix run nixpkgs#nixos-facter` |
| `/root/.ssh/authorized_keys` on `server` | Unreadable without root | The owner checks, or adds the key in step 4 |
| Option C composition (generated `.vendomat/` import with inputs) | Not yet run | One temp fixture |
| Attic upload of devenv outputs | No Attic server in fixtures | A push to the real cache |
| Machines boot-time recovery | The direct-boot VM cannot test it | A VM with a persistent disk |

## 3.4 Design rules that follow

1. Hard checks are **assertions**, never tasks. Tasks are for warnings and for `devenv test`.
2. `devenv build` and `devenv eval` skip assertions. `vendomat push` must call a check first.
3. The pre-resolver warns when a workspace or local yaml redeclares a generated input, because the override replaces the whole entry.
4. Prefer plain nixpkgs (`github:NixOS/nixpkgs/<rev>`) over `devenv-nixpkgs` where offline shells matter.
5. Under `outputs`, only derivations.
6. The module owns `machines.<h>.nixos`; the owner writes `vendomat.inventory.<h>.nixos`.
7. The system CLI is a release build of the patched fork, so `require_version: true` is enforced.

- Pre-resolver input types other than git and github, and two imported repos that disagree on one input.
